## Part B — what a full-credit answer includes

**8.** *Modularity:* LLM tools can't be allowed to write all over a repository; teams need boundaries so generated changes don't break each other's work. Developers long paid "lip service" to modularity and relied on brute force, which won't scale with generated code, so a "reckoning" will make modularity central again. *Legibility:* LLMs process language as people do, so code whose structure and names match the problem domain is easier for both LLMs and humans to read, generate correctly, and check.

**9.** Good ideas: incrementality, and judging progress by delivered value rather than lines of code (both predate Agile). Damage: contempt for "big design up front" lumped thoughtful design with excess documentation and encouraged just coding. Reuse: every social media app needs authentication, posting, commenting, following, and karma. These are familiar concepts that should be reused, with innovation focused where it's needed. Methods assume greenfield and reinvent them.

## Part C — rubric (10 points)

- **Diagnosis (2):** Pre-digested problems teach coding to a spec; real difficulty is understanding and formulating the domain problem (track power, adjacent cranes).
- **Cross's idea (2):** Problem and solution co-evolve; artifacts teach you about the problem.
- **Concrete course changes (4):** For example: projects with real stakeholders and messy domains; required problem framing and concept/domain models before coding; critique of exemplars (Shaw); reflection journals (Schön); LLMs used to generate prototypes quickly as probes of the problem (Beck's cheap experiments); assessment of specifications and design rationale, not just passing tests.
- **Cross-chapter (2):** Shaw (problem setting, exemplars, curriculum as design), Beck (act of creation changes what you want; pre-med analogy), Krishnamurthi (do-it-twice, the design crit).
